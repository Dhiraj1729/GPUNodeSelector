Project purpose
---------------

Build a Kubernetes AI workload control plane consisting of:

1. An AIWorkload Custom Resource Definition.
2. A Go/Kubebuilder operator with a careful, idempotent reconciliation loop.
3. A fake GPU device plugin for laptop development.
4. A multi-node local Kubernetes cluster containing CPU and simulated GPU nodes.
5. A mock AI inference workload that can run without CUDA.
6. End-to-end tests demonstrating scheduling, GPU capacity exhaustion, recovery, update, drift correction, and deletion.

This is not an LLM application and is not an autoscaling or telemetry project. It is a Kubernetes control-plane and device-resource-management project.

Core architecture
-----------------

The architecture must preserve Kubernetes responsibility boundaries:

AIWorkload CR
    |
    v
AIWorkload Operator
    |
    | creates Deployment and Service
    | adds GPU resource request
    | adds GPU product selector
    | adds GPU-node toleration
    v

    |
    v
Default Kubernetes Scheduler
    |
    | selects a suitable node
    v
Kubelet
    |
    | allocates a fake GPU through the device plugin

The operator expresses placement requirements. It must not directly bind pods to nodes and must not set spec.nodeName.

Do not modify, fork, replace, or extend kube-scheduler for the MVP.

Responsibility boundaries
-------------------------

Cluster bootstrap:

- Creates the multi-node local cluster.
- Labels the simulated GPU node.
- Taints the simulated GPU node.
- Leaves at least one worker available for ordinary CPU workloads.
- Deploys the fake GPU device plugin.

Fake device plugin:

- Advertises fake GPU devices to the kubelet.
- Uses an extended resource such as ai.dhiraj.io/gpu.
- Reports a configured number of healthy fake devices.
- Supports the kubelet Allocate request.
- Does not perform real CUDA operations.

AIWorkload operator:

- Watches AIWorkload resources.
- Creates and owns a Deployment and Service.
- Adds GPU requests, product selectors, and tolerations to the pod template.
- Reconciles desired state repeatedly and idempotently.
- Repairs drift in fields owned by the operator.
- Reports useful workload and scheduling status.
- Does not manually choose nodes.
- Does not manually reserve or count GPUs for scheduling decisions.
- Does not label or taint nodes.
- Does not cap requested replicas based on a precomputed capacity count.
- Lets the scheduler remain the source of truth for concurrent resource allocation.

Default scheduler:

- Filters nodes by extended-resource capacity.
- Applies the node selector or affinity.
- Applies taints and tolerations.
- Selects the final node.
- Leaves excess replicas Pending when GPU capacity is exhausted.

Kubelet:

- Publishes device-plugin capacity in Node status.
- Handles allocation of individual fake device IDs.
- Releases allocations when pods terminate.

AIWorkload API
--------------

Use:

apiVersion: ai.dhiraj.io/v1alpha1
kind: AIWorkload

Proposed API:

apiVersion: ai.dhiraj.io/v1alpha1
kind: AIWorkload
metadata:
  name: mock-llama
  namespace: ai-workloads
spec:
  image: gpu-node-selector/mock-inference:dev
  replicas: 2
  port: 8080

  gpu:
    product: A100
    count: 1

  resources:
    cpu: 100m
    memory: 128Mi

The exact Go types should use Kubernetes-native types where appropriate, such as resource.Quantity and metav1.Condition.

Validation/defaults:

- spec.image is required.
- spec.replicas defaults to 1 and cannot be negative.
- spec.port defaults to 8080 and must be a valid container port.
- spec.gpu is required for this focused GPU MVP.
- spec.gpu.product is required.
- spec.gpu.count must be an integer greater than zero.
- CPU and memory may be optional but must validate when provided.
- Use Kubebuilder validation and default markers.
- Do not expose implementation details such as the extended-resource name to ordinary AIWorkload users unless there is a strong reason.

The operator translates:

spec.gpu.count: 1

into:

resources:
  limits:
    ai.dhiraj.io/gpu: 1

It translates:

spec.gpu.product: A100

into a required node selector or required node affinity matching:

ai.dhiraj.io/gpu-product: A100

It automatically adds the GPU-node toleration.

The generated Deployment must not use nodeName.

Status design
-------------

The CR status should include at least:

status:
  observedGeneration: 3
  phase: CapacityBlocked
  desiredReplicas: 3
  updatedReplicas: 3
  readyReplicas: 2
  availableReplicas: 2
  pendingReplicas: 1
  endpoint: http://mock-llama.ai-workloads.svc:8080
  conditions:
    - type: Ready
      status: "False"
      reason: InsufficientGPU
      message: One replica is pending because ai.dhiraj.io/gpu capacity is unavailable
      observedGeneration: 3
      lastTransitionTime: ...

Suggested phases:

- Pending
- Provisioning
- Running
- Degraded
- CapacityBlocked
- Failed

Use metav1.Condition and conventional Kubernetes condition handling.

At minimum, consider conditions such as:

- Ready
- Progressing
- Scheduled
- CapacityAvailable

Status must distinguish, where reasonably possible:

- Insufficient ai.dhiraj.io/gpu capacity.
- GPU product/node selector mismatch.
- Untolerated taint or other scheduling constraints.
- Image pull failure.
- Deployment unavailable.
- Normal rollout progress.

Do not depend only on parsing human-readable text if structured Pod conditions and reasons are available. Where Kubernetes only exposes useful detail in a message, isolate parsing behind a focused helper and test it.

Set status.observedGeneration so users can distinguish current status from stale status.

Avoid unnecessary status writes. Patch status only when its semantic value has changed.

Operator reconciliation requirements
------------------------------------

The main engineering focus is a high-quality reconciliation loop.

The reconciler should follow this general shape:

1. Fetch AIWorkload.
2. Return successfully on NotFound.
3. Validate or handle invalid desired state safely.
4. Reconcile the desired Deployment.
5. Reconcile the desired Service.
6. Inspect Deployment and relevant Pods.
7. Derive status and conditions.
8. Patch status only if changed.
9. Requeue only when necessary.

Implementation requirements:

- Desired Deployment and Service construction should live in focused, testable builder functions.
- Use stable labels identifying the AIWorkload name and UID where appropriate.
- Use controller OwnerReferences.
- Watch owned Deployments and Services.
- Arrange for relevant Pod changes to trigger reconciliation, even though pods are indirectly owned through ReplicaSets. A label-based watch/mapping function is acceptable.
- Use CreateOrPatch, CreateOrUpdate, or server-side apply deliberately and document the choice.
- Mutate only fields owned by this operator.
- Preserve server-assigned Service fields such as clusterIP.
- Preserve unrelated metadata where reasonable.
- Detect an existing resource with the expected name that is controlled by someone else; do not silently adopt or overwrite it.
- Make repeated reconciliation safe.
- Do not create duplicate resources.
- Handle resource-version conflicts through normal controller-runtime retry behavior.
- Return errors rather than hiding them.
- Use structured logging with namespace, name, generation, and reconciliation outcome.
- Keep RBAC least-privileged.
- Do not use a finalizer for ordinary Deployment and Service cleanup; OwnerReferences and garbage collection are sufficient. Add a finalizer only if a real external cleanup obligation is introduced.
- Do not add artificial sleep calls to the reconciler.
- Avoid a hot requeue loop.
- Use event-driven reconciliation and a bounded RequeueAfter only where necessary for pending state refresh.

Drift and update behavior
-------------------------

Demonstrate that the operator corrects drift in fields it owns.

Examples:

- If someone changes Deployment replicas from 2 to 1 while AIWorkload requests 2, the operator restores 2.
- If someone removes the GPU resource limit, the operator restores it.
- If someone removes the GPU node selector or toleration, the operator restores it.
- If someone changes an unrelated annotation not owned by the operator, it should not be needlessly deleted.
- Updating AIWorkload replicas updates the Deployment.
- Updating its image triggers a normal Deployment rollout.
- Updating GPU count or product updates the pod template and rollout.
- Reapplying an unchanged AIWorkload should cause no harmful changes.
